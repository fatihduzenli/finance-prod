# PLAN-012e-3 — Follow-ups F1 and F2 of Step 12e: "Check" as a manual payment method; the builder's lines table in a scroll region

**Owner's text:** 2026-10-22 ("add 'Check' as its own manual payment method (label and reference
'check number'), alongside Zelle and wire, in a small follow-up with the lines-table width; not
needed before this push"). **Author:** Fable. **Implementation:** Opus, one batch. **Status:**
Phase A plan; no pending decision.

## 1. Restated objective

A staff member who receives a check records it as a check, not as "other": every place a manual
payment is recorded (Add payment on the store and operator workspaces, the builder's Record
payment now, the insurance and one-off charge payment forms, the lease-end and deposit refunds
where a payment method is chosen) offers Check beside Zelle and wire; when Check is chosen the
reference field is named "Check number"; the ledger, the statement, the payment page and the
exports show "Check". The invoice builder's lines table no longer widens the page past the
viewport: it sits in the scroll region the other wide tables use.

## 2. Affected packages

`backend/ledger` (`models.PaymentMethod`, one choices migration, `services/rent_run.MANUAL_METHODS`,
`forms.MANUAL_METHOD_CHOICES` and the payment forms, the templates that label the reference,
`invoices/_draft_form.html`), `backend/tests`, `docs/`. Out of scope: `payments/` (the processor
never sees a manual payment's method), refunds (`RefundMethod` already has `check`), the CSV
column keys, Step 13.

## 3. Decisions

- **D1.** `PaymentMethod.CHECK = "check", "Check"`, a new stored value (the frozen-value list in
  `tests/test_plan012c_design_d_adversarial.py` is updated by Fable in the same batch); a
  choices-only migration (`ledger/0048_check_method`, `AlterField` on every field that uses
  `PaymentMethod.choices`: `payments.method`, `lease_credits.method`, `deposit_resolutions.method`
  and any other the autodetector names; `sqlmigrate` prints no-op). No data migration: payments
  recorded as "other" before stay "other" (their note or reference says "check" where staff wrote
  it).
- **D2.** `rent_run.MANUAL_METHODS = (ZELLE, WIRE, CHECK, OTHER)` in that order;
  `forms.MANUAL_METHOD_CHOICES` the same order with the labels "Zelle", "Wire", "Check", "Other";
  every manual-payment form and `invoice_builder.PaymentInput` accept `check` through those two
  constants (no form lists methods by hand). The CHECK constraints that name methods, if any,
  gain the value (the constraint test `test_every_constraint_has_a_case` names them).
- **D3.** The reference field: label "Reference", help "A Zelle confirmation, a wire reference or a
  check number; never an account number"; while Check is chosen the label reads "Check number"
  (the `data-shown-when` script pattern, or a `data-label-when="<method id>=check"` attribute the
  same script applies; without script the label stays "Reference" and the help names the check
  number). The guard on the reference (no card or account number, the existing validator) is
  unchanged: a check number is a short number and passes; a 13–19 digit Luhn run is refused as
  today.
- **D4.** Labels: "Check" wherever `get_method_display` renders (the payment page, the ledger, the
  statement, the store tabs, the e-mail lines that name a method, the PDF statement); the CSV
  exports write the label in their method column as they do for the others (keys unchanged).
- **D5.** The builder's lines table is wrapped in the `{% responsive_table "scroll" %}` region (or
  the `.table-scroll` wrapper it renders), so the page stays within 1,280 px; the builder's
  script keeps working on the table inside the region (`invoice_lines.js` selects by id); the
  visual baselines of the builder page are regenerated by Fable in the Playwright image.

## 4. Interface contract

```
ledger.models.PaymentMethod: + CHECK = "check", "Check"
ledger.services.rent_run.MANUAL_METHODS = (PaymentMethod.ZELLE, PaymentMethod.WIRE, PaymentMethod.CHECK, PaymentMethod.OTHER)
ledger.forms.MANUAL_METHOD_CHOICES: the same four, labels Zelle, Wire, Check, Other
Migration: ledger 0048_check_method (AlterField choices only)
Templates: the reference field's label switches to "Check number" while method == check (script), help names the check number (no script)
invoices/_draft_form.html: the lines table inside the scroll region
```

## 6. Test plan (before implementation)

Opus: a check recorded through each form (store Add payment, operator Add payment, the builder's
Record payment now, the insurance and one-off payment forms) stores `method == "check"` and shows
"Check" on the payment page, the ledger, the statement and the store tab; the reference label
switches with the method (markup and an e2e case in `tests/e2e/test_dependent_fields.py`); the
help names the check number; the migration is in the round-trip list and prints no-op; the CSV
method column writes "Check"; the builder page's lines table is inside `.table-scroll` and the
page's scroll width at 1,280 px equals the viewport (an e2e case). Fable: the frozen-value list
updated; adversarial: a check number that is a 16-digit Luhn run is refused with nothing written;
a 9-digit routing-like number next to a longer run is refused; a check number with markup is
escaped on the payment page; `method=check` posted on a form that offers only autopay methods
is refused; the builder's `record` path with `check` writes the same rows as with `zelle`.

## 7. Risk register

A new stored value (frozen by test, updated deliberately); a choices-only migration; the label
switch is a convenience over the no-script label; the scroll region must not break the builder's
script (ids unchanged) nor the labels of Batch E of 12c (the visually-hidden labels stay inside
the table). No processor call changes.

## 8. Acceptance criteria

On staging: a check is recorded from Add payment and from the builder with its check number, and
shows as "Check" on the payment page and the statement; the builder page does not scroll sideways
at 1,280 px; the visual job is green.
